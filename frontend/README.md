# `frontend/`

O diretório `frontend/` é o repositório central de toda a interface de usuário e experiência de interação do nosso aplicativo móvel. A intenção inicial para esta camada do sistema é utilizar o ecossistema React Native em conjunto com o Expo, garantindo um desenvolvimento ágil e a entrega de um aplicativo funcional tanto para dispositivos Android quanto iOS a partir de uma única base de código em TypeScript. Ressaltamos que esta é a arquitetura inicial planejada para o Produto Mínimo Viável (MVP), e tudo pode mudar caso haja a necessidade técnica de ejetar o Expo para acessar módulos nativos muito específicos no futuro. Neste momento, o objetivo é que esta pasta contenha todos os componentes visuais, telas de navegação, e a lógica de consumo da nossa API em Python. A estrutura está desenhada para separar claramente a apresentação visual das regras de negócio do lado do cliente. Componentes reutilizáveis, como botões padronizados e cartões de exibição de produtos farmacêuticos, ficarão isolados, enquanto as telas principais orquestrarão a exibição dos dados de laboratórios e distâncias. Além disso, o gerenciamento de estado global e as chamadas de rede estarão estritamente modularizados aqui. O uso estrito do TypeScript tem a intenção inicial de documentar implicitamente as estruturas esperadas, minimizando erros de tempo de execução e facilitando a manutenção futura.

## `src/`

A pasta `src/` atua como o cofre principal e o diretório raiz para todo o código-fonte operacional e autoral da nossa interface móvel desenvolvida em React Native. A intenção inicial deste diretório no sistema é encapsular estritamente o domínio visual e as lógicas dinâmicas de cliente da aplicação, separando de forma absolutamente clara e inegociável a interface do usuário das regras de configuração externa. Isso significa manter as telas isoladas dos metadados de empacotamento do Expo, dos scripts do Node.js ou das definições tipográficas pesadas do TypeScript que habitam obrigatoriamente a raiz do projeto. Ao concentrar todos os módulos de execução dinâmica dentro desta fronteira estrutural estrita delineada pelo `src/` (abreviação universal para source, ou código-fonte), nós adotamos indiretamente os princípios de design de software limpo, o que facilita imensamente a localização visual de bugs e a manutenção diária do código por qualquer engenheiro de software que ingressar na equipe. Neste primeiro momento, focado inteiramente na entrega rápida e funcional do Produto Mínimo Viável (MVP) de scraping de farmácias para a próxima semana, manteremos todo o ecossistema de telas de busca, componentes visuais reaproveitáveis, hooks de gerenciamento de estado e algoritmos de comunicação com a nossa API Python rigorosamente confinados aqui dentro, garantindo um nível altíssimo de coesão interna. Naturalmente, no desenvolvimento ágil de produtos digitais, tudo pode mudar à medida que o projeto escalar e novas necessidades arquiteturais surgirem no horizonte do final do ano. Se no futuro decidirmos, por exemplo, expandir este monorepo dividindo o código entre o aplicativo móvel atual e um novo painel web administrativo em React.js para gerenciar manualmente os laboratórios e medicamentos catalogados, essa pasta `src/` será o ponto de partida lógico para a extração de componentes universais. A sua existência imutável garante que o repositório permaneça imaculadamente limpo, organizado e livre da poluição sistêmica gerada pela mistura acidental de scripts de infraestrutura de compilação com o código de renderização JSX das telas.

- `src/components/` A pasta `src/components/` é concebida como o arsenal definitivo de blocos de construção visuais e de interface de usuário estritamente reutilizáveis para o nosso aplicativo móvel. A intenção inicial deste sistema é abrigar elementos atômicos e moleculares da interface, tais como botões padronizados, campos de entrada de texto para a busca de medicamentos, e os cartões complexos que exibirão o nome, o laboratório e o preço de cada remédio raspado pelo backend. Ao isolar a apresentação visual estática das regras de negócio complexas e das chamadas de rede, nós garantimos que a equipe de engenharia possa alterar o design de um botão de compra em um único arquivo e ver essa modificação refletida instantaneamente em todo o aplicativo sem gerar efeitos colaterais. É fundamental pontuar, no entanto, que esta é a arquitetura embrionária planejada para suportar a entrega rápida do MVP, e absolutamente tudo pode mudar à medida que o design system interno da empresa evoluir ou se tornar substancialmente mais sofisticado e fragmentado. Se no futuro o volume de telas crescer de forma exponencial, poderemos precisar subdividir rotineiramente esta pasta em subdiretórios categóricos e modulares, como componentes de formulário, componentes de layout global e componentes estritos de tipografia, adotando metodologias de design atômico mais rigorosas. Por enquanto, a disciplina de manter a camada visual estrita e completamente passiva (dumb components) aqui dentro previne o temido acoplamento excessivo de código e facilita imensamente a criação e manutenção de testes de snapshot visuais no ecossistema do React Native.
- `src/screens/` O diretório `src/screens/` atua primariamente como a camada de orquestração superior no ciclo de vida do frontend, onde os blocos visuais menores ganham vida e se transformam em páginas completas, interativas e navegáveis pelo usuário final do aplicativo móvel. A intenção inicial deste sistema é abrigar componentes React de alto nível, os chamados "smart components", que são inteiramente responsáveis por ditar o ciclo de vida da renderização da tela, despachar ações assíncronas para o gerenciamento de estado global e invocar diretamente os métodos de comunicação com a nossa API construída em FastAPI. Cada arquivo de tela aqui mapeado, como a `BuscaScreen` ou a `DetalhesMedicamentoScreen`, servirá rigorosamente como um contêiner lógico que amarra os dados de localização geográfica obtidos do celular com a exibição fluida da lista de farmácias e laboratórios mais próximos e baratos. Obviamente, no dinâmico e implacável ecossistema de desenvolvimento mobile focado no consumidor, tudo pode mudar de um dia para o outro conforme os indispensáveis testes de usabilidade e conversão com usuários reais revelem atritos ou novos padrões de navegação não antecipados. Se descobrirmos posteriormente que a retenção e o engajamento do usuário exigem fluxos de telas radicalmente diferentes ou unificados, as robustas responsabilidades atualmente concentradas nestes arquivos individuais poderão ser rapidamente pulverizadas, fundidas ou delegadas a novos middlewares. A longo prazo, poderemos adotar padrões de injeção de dependência mais refinados, mas neste primeiro momento, a segregação inegociável entre o que é "tela" (possuindo comportamento e dados dinâmicos) e o que é meramente "componente" (possuindo apenas interface visual passiva) garante a tração, a velocidade e a clareza analítica de que precisamos urgentemente para entregar a primeiríssima versão funcional do nosso catálogo de forma íntegra até a semana que vem.
- `src/services/` A pasta `src/services/` tem a missão crítica de isolar completa e hermeticamente toda a complexidade da comunicação externa e das requisições de rede (network requests) para fora do ciclo de vida dos componentes do React Native. A intenção inicial deste sistema é centralizar a configuração de clientes HTTP, como o Axios ou a API nativa Fetch, abrigando funções assíncronas dedicadas que sabem exatamente como formar a URL correta, injetar tokens de autorização nos cabeçalhos e disparar os verbos HTTP adequados (GET, POST) contra o nosso backend FastAPI de scraping de farmácias. Quando uma tela precisa da lista de medicamentos filtrados pelo laboratório X, ela não cria a requisição do zero; ela apenas invoca um método contido aqui, mantendo a tela completamente cega e protegida em relação à infraestrutura de rede subjacente. É vital ter a consciência plena de que, no caótico ambiente de redes móveis (3G/4G instáveis), tudo pode mudar arquiteturalmente para garantir a resiliência do aplicativo e a boa experiência do usuário. Se a latência das buscas começar a impactar a interface ou se o nosso servidor de Python demorar para raspar múltiplas farmácias em tempo real, esta exata pasta precisará evoluir abruptamente. Teremos que implementar rotinas agressivas de reconexão automática (retries), interceptadores globais de tempo de esgotamento (timeouts), mecanismos de circuit breaker, ou até mesmo acoplar bibliotecas avançadas de sincronização de dados offline, como o React Query ou WatermelonDB, para manter os preços armazenados localmente no cache do dispositivo móvel.
- `App.tsx` O arquivo `App.tsx`, repousando na raiz diretiva do frontend, é indiscutivelmente o coração lógico e o alfa absoluto de toda a árvore de renderização do nosso aplicativo móvel no ecossistema do React Native. A intenção inicial deste sistema encapsulado neste único e vital arquivo é atuar como o ponto de entrada principal e inflexível onde o motor do JavaScript inicia a construção interativa do que o usuário efetivamente verá na tela do seu celular. É rigorosamente nas linhas deste arquivo que nós vamos circundar a nossa aplicação com os provedores de contexto indispensáveis, inserindo os invólucros do gerenciador de navegação global (React Navigation), os provedores de estado da aplicação (como Context API ou Redux), e os essenciais provedores de temas visuais (Dark Mode / Light Mode). Ele não deve, sob hipótese alguma, conter lógicas de negócio específicas de farmácias ou regras de cálculo de distância, funcionando apenas como o maestro que garante que todos os subsistemas transversais estejam devidamente instanciados antes que a primeira tela de busca seja efetivamente montada para o usuário. Dada a urgência de colocarmos a prova de conceito operacional até a semana que vem, manteremos este arquivo o mais limpo, coeso e linear possível, injetando apenas a base da navegação em pilha (Stack Navigation) para que possamos transitar entre a visualização do catálogo e a tela de detalhamento de um laboratório específico sem maiores complexidades estruturais. Entretanto, na engenharia de software voltada para o consumidor final, a única certeza é a volatilidade, e de fato, tudo pode mudar assim que o projeto tracionar e o site completo se materializar no horizonte do final do ano. Quando precisarmos lidar com fluxos intrincados de autenticação persistente (onde o aplicativo decide se abre a tela de login ou a tela inicial de busca dependendo do token salvo), ou quando precisarmos inicializar bibliotecas pesadas de observabilidade analítica, captura passiva de falhas (como Sentry ou Crashlytics), e recepção de notificações push via nuvem, este arquivo inchará em responsabilidades de inicialização. Ele inevitavelmente evoluirá de um simples componente raiz para um complexo e intrincado orquestrador de processos de ciclo de vida (bootstrapping) de alto nível e altíssima criticidade de sistema operacional.
- `app.json` O arquivo `app.json` funciona estritamente como o manifesto declarativo e o passaporte oficial do nosso aplicativo móvel perante o rigoroso ecossistema de compilação da nuvem do Expo e das lojas oficiais de distribuição de software (Apple App Store e Google Play Store). A intenção inicial deste sistema puramente configuracional é ditar inflexivelmente, sem a necessidade de escrever uma única linha de código nativo em Java, Kotlin ou Swift, as propriedades mais elementares e vitais da identidade do software que estamos construindo. É exatamente dentro deste arquivo JSON estruturado que definiremos o nome público que aparecerá sob o ícone no celular do usuário (ex: "BuscaFarma"), os caminhos exatos para os arquivos visuais de alta resolução que compõem o ícone oficial da marca e a tela de carregamento dinâmico (splash screen), bem como o identificador único e global de pacote (bundle identifier). Ele também é o guardião responsável por declarar antecipadamente quais permissões sistêmicas o nosso aplicativo exigirá do hardware do usuário, como o acesso inescapável ao módulo de GPS (Location API) para calcularmos, via fórmula matemática de Haversine no backend, a distância exata em metros até a drogaria mais barata da região mapeada. Para o nosso MVP que será distribuído para uma base interna ou de testadores na próxima semana através do aplicativo Expo Go, este arquivo servirá apenas como um identificador básico, mantendo suas configurações cruas e minimalistas, focadas inteiramente no funcionamento intocável no ambiente de rede local (localhost) do desenvolvedor da máquina host. Contudo, ao mirarmos a consolidação do sistema de scraping em um site e plataforma de grande escala, é imperativo compreender que absolutamente tudo pode mudar nas diretivas de compilação deste manifesto. O processo de publicação real (deployment) em lojas de aplicativos exige uma granularidade colossal de configurações restritivas. Quando formos compilar os binários independentes (.APK ou .IPA), este arquivo precisará ser drasticamente expandido e minuciosamente configurado para incluir chaves de rastreamento de anúncios e métricas de conversão, diretivas complexas de roteamento profundo (Deep Linking - para que um link compartilhado no WhatsApp abra diretamente no remédio específico dentro do app), restrições severas de orientação de tela responsiva, e certificados criptográficos de assinatura de produção em nuvem. Ele é, no final das contas, o contrato imutável entre a nossa ideia concebida em React Native e as intransigentes exigências de segurança e padronização dos ecossistemas vitais da Apple e do Google.
- `package.json` O arquivo `package.json` é indiscutivelmente o registro de governança, o mapa de dependências absolutas e o painel central de comandos do nosso ambiente de desenvolvimento para a interface do aplicativo móvel baseado em Node.js. A intenção inicial deste sistema declarativo é manter um controle ferrenho, versionado e implacável sobre cada biblioteca de terceiros, módulo visual pré-fabricado ou utilitário matemático de TypeScript que o nosso frontend importará para agilizar a construção do catálogo de farmácias. Quando decidirmos utilizar bibliotecas robustas e padronizadas da comunidade, como o `react-navigation` para o roteamento suave entre as telas, o `axios` para as requisições HTTP seguras, ou o `lucide-react-native` para iconografia moderna, é o `package.json` que cravará na pedra do repositório a versão exata que funcionou hoje, garantindo que o aplicativo não quebre violentamente no computador de outro desenvolvedor da equipe amanhã por conta de atualizações invisíveis em pacotes não rastreados. Além disso, ele hospeda a valiosa chave "scripts", funcionando como um pequeno maquinário de automação interna onde deixamos configurados os atalhos de rotina (como o popular `npm start` ou `npm run android`) para instanciar o servidor Metro Bundler com parâmetros customizados. Visando a entrega incrivelmente rápida e de alto risco estipulada para a primeira demonstração viável do produto (MVP) em apenas sete dias, este manifesto manterá um número mínimo e pragmático de dependências de produção, priorizando somente as ferramentas estritamente indispensáveis para não sobrecarregar demasiadamente o tamanho final do pacote do aplicativo e manter o tempo de carregamento no simulador o mais rápido possível para a equipe de engenharia iterar na interface de scraping. Entretanto, como o escopo arquitetural planejado visa escalar até o final do ano transformando essa ferramenta num agregador de laboratórios poderoso, precisamos manter o horizonte de que absolutamente tudo pode mudar de forma drástica na composição das nossas ferramentas. Com o crescimento e estabilização do projeto base, este arquivo certamente inchará e será agressivamente reestruturado para acomodar pesadas dependências de desenvolvimento (devDependencies), tais como suítes inteiras de testes de unidade e mutação (Jest, React Native Testing Library), formatadores de código e linters estritos em regras arquiteturais (ESLint, Prettier), além de possíveis ferramentas integradas de engenharia reversa de build nativo e scripts de integração e entrega contínuas (CI/CD) voltadas para fluxos automatizados em plataformas de nuvem de DevOps.
- `tsconfig.json` O arquivo `tsconfig.json` reside na raiz do diretório frontend e age primariamente como a lei inquestionável e o juiz implacável sobre como o nosso código-fonte em TypeScript deve ser analisado, interpretado e finalmente transpilado com segurança para o JavaScript puro que o motor dos smartphones modernos consegue executar de maneira fluida. A intenção inicial deste sistema de configuração estática é blindar severamente o nosso processo de desenvolvimento contra falhas humanas previsíveis, forçando o compilador subjacente do TypeScript a operar no seu modo mais restrito, defensivo e seguro possível (o aclamado e temido strict mode). Isso assegura matematicamente que nenhum desenvolvedor da equipe conseguirá, intencionalmente ou por puro descuido provocado pela pressa do prazo curto, repassar silenciosamente uma string aleatória para um componente visual sensível que estava expressa e tipograficamente aguardando um array numérico contendo as distâncias calculadas em quilômetros das farmácias. Ele estipula também as complexas regras vitais de resolução dos módulos virtuais internos e os caminhos de mapeamento de pastas (path aliases), permitindo que adotemos importações de arquivos muito mais elegantes e curtas (como `import { Button } from '@/components/Button'`), erradicando de vez a necessidade tortuosa de utilizar múltiplos e confusos pontos e barras de navegação retroativa de diretórios relativos. Para a nossa atual janela de trabalho focada incansavelmente na construção do Produto Mínimo Viável (MVP), contaremos amplamente com a robusta configuração padrão fornecida gratuitamente na geração do projeto por meio das ferramentas de interface de linha de comando oficial do framework Expo. Essa base sólida cobre de antemão perfeitamente a vasta maioria das necessidades semânticas mais prementes, garantindo tipagem consistente, autocompletar inteligente nas IDEs de edição e checagem de nulidade em tempo de projeto sem gerar entraves paralizantes na produtividade diária dos engenheiros envolvidos. No entanto, o planejamento estratégico do ciclo de vida de software dita sem clemência que absolutamente tudo pode mudar nas exigências sistêmicas conforme o sistema cruze a barreira da simplicidade. Se a aplicação de scraping e agregação passar a exigir uma refatoração gigantesca ou até mesmo iniciar uma migração para uma arquitetura complexa orientada ao paradigma de domínio pesado no frontend ao longo do ano corrente, este modesto arquivo de tipagem se tornará invariavelmente o verdadeiro epicentro nevrálgico de longas sessões de debates técnicos rigorosos, moldando e reajustando dezenas de minúsculas variáveis de inferência matemática e exclusões de bibliotecas em conflito de tipos para garantir a escalabilidade absoluta do monorepo perante os desafios de um sistema gigantesco.
